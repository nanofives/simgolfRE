# 0x10015230 Tile::resetFaceTextures

## Role (from the naming pass, not a C3 purpose)
Clears the path flag byte b2 when b0 is set, writes every face texture (count +0x44) from g_textures: [0][+0x28][0] for type 0, [type][variation][3] otherwise, then calls Tile::reblendNeighbourhood (`re/names/terrain_3.tsv`)
System writeup: `re/analysis/systems/terrain_2.md`, `re/analysis/systems/terrain_3.md`.

## Purpose
Gives every face of a tile one and the same texture, which is what the two types that have no edge blending - 0 and 9, the only two Tile::setTypeId routes here - need before the neighbourhood is re-blended. A tile that carries a path has its path-type flag cleared first (byte [this+0x208] at 0x10015252, je 0x1001525a, store 0 at 0x1001525f), the opposite of what Tile::setTypeId had just written there. Which texture depends on the tile's own type (cmp [this+0x24], 0 at 0x10015269, jne 0x1001526d): type 0 takes g_textures[0][this->sub][0], the dword at 0x100687f8 + [this+0x28] * 0x24 (imul 0x10015292, load 0x1001529e), and every other type takes g_textures[type][variation][3], the dword at 0x100687f8 + type * 0x384 + [this+0x240] * 0x24 + 0xc (imul 0x100152cf, imul 0x100152de, load 0x100152ea). Both loops run over `i < this->faceCount` at [this+0x44] (jge 0x1001528a and jge 0x100152c7) and store at [this + i*0x38 + 0x6c] (0x100152a4, 0x100152f1), so a face count of 0 or less writes no face and the two loops are the only difference between the branches. It ends by re-blending the neighbourhood (call 0x100152fa of the thunk 0x1000103c), which rewrites all eight faces again for every type Tile::isSolidType 0x100154a0 accepts - and that excludes 0 and 9, so on the types the caller sends here the loop's writes are what survives. Reimplemented in `shim/src/re/c3bk.cpp`; path-1 A/B GREEN: Tile::resetFaceTextures (14 vectors, 14 distinct results, 13 changing state, `log/diff/00015230_Terrain_Tile_resetFaceTextures.path1.csv`).
