## Group 7: the zoom box's ball marker

mainLoop P5 (S3.25's call log, 25_notes.md): Surface_blit3 magnifies the view, then per name label Widget_readPixel(root, 2x - 0x190,
2y - 0x12c) 0x00478df0 and, when it is 0x7fff (0x00418b98), Surface_drawScaled(g_sprite567b08, root, esi - 2, edi - 1, 1, 1, 1, 0) at
0x00418bb8. The port transcribes it (tick_frame.inc ML+0x95d3..ML+0x95f8), but Widget_readPixel was a drop (tick.cpp kDrops: "its only
use gates a dropped sprite draw") listed as not drawing (gfx.cpp kNotDrawing), so with a backend attached it still returned 0 and the
port never made the draw. The box showed the magnified scene (zoom_box: 2206 2206 2627 2627 | 0000 0000 7fff 7fff | ...), 15 of 16 px
off the marker (the equal px is the test point (144, 90), 0x7fff in both).
The marker content was right already: g_sprite567b08 is the 4 x 4 cut of BLDG.PCX at (0xc4, 0) (gfx_hud.cpp loadInterfaceArt+0x3782;
the image loaded at loadInterfaceArt+0x3728 is f_strpool_4c5ec8+0x1c = `bldg.pcx`), whose bytes through the file's palette (`>> 3`) are
the original's 16 px: ec:779c f5:7fff f5:7fff ed:5294 / f5 f5 f5 ec:779c / f5 ec ec ed / ee:4210 ed:5294 ee:4210 05:2108.
Fix: body `Widget_readPixel` in family `pixel` (gfx_pixel.cpp), from c3db.cpp GetPixel_re (C4): 0 for x < 0, y < 0, x >= width,
y >= height; else the 16-bit word, handed back to the frame code with gfx_take_value (Text_put's mechanism, S3.7). Without a
backend the drop returns 0 as before. The name left kNotDrawing (gfx.cpp), framegate.py NOT_DRAWING and the copies in test_gfx.py /
test_framegate.py. The port's only call site is tick_frame.inc ML+0x95d3 (hitTestTree 0x0047f340, the other caller, is not ported).

## Group 4: the selected-golfer sprite (golfer_stories season_end)

The port's GameState at the snapshot (SG_GFX_SNAPSTATE): g_ui_569498 = 1, f_w_4c2e00[2] = -2. f_w_4c2e00 is class sim, so -2 is the
original's value too (the boot gate compares it every frame). P4 (0x004159f7..0x00415a3f) tests only `!= -1`, so the original reads
"golfer -2": g = -2 << 8, record 0x005792b8, inside g_sprites5791f8 (SpriteRef[16], pointer class). +8 / +0xc = element 4's +0x18 /
+0x1c (the cut's requested width / height: 80, 80 in all 205 segment start images, so the sprite lands at (60, 70), S3.25's box), and
+0x21 = byte 1 of element 5's handle +4 (nonzero in all 205 images). The port keeps SpriteRef fields only in the graphics backend
(Sprite8; S2.8's gfx_sprite_cut precedent), so its GameState reads 0 there and P4 returned before the draw.
Fix: tick_frame.inc P4_selectedSprite reads those three words through gfx_sprite_ref_read (gfx_pixel.cpp) when a backend is attached:
a read inside a SpriteRef the backend holds answers +0x10 kept w, +0x14 kept h, +0x18 / +0x1c cut w / h, +0x20 / +0x24 trims (c3ee.cpp
CropSprite_re's stores), and a handle byte (+4..+7) as 1 (U-1950); anything else falls back to the GameState word. Only the dropped
Sprite_draw and its position depend on it. The cut (loadInterfaceArt+0x3a51: course1.pcx at (0x225, 0xd7), 43 x 21) holds 707 bytes of
0xfc and 196 of 0xff, and the original changes exactly 707 px of the box (S3.25): the plane blit's block 4. Result: season_end PASS.

## Group 5: the cursor diamond's connector (cov_k3_camera y_inj3): U-1834 settled, not fixed

worldToScreen(0xc7ff, 0xd800) is tile (49, 54): cell = 49 * 50 + 54 = 2504, past the 2,500-byte grids. In the segment image
cov_k3_camera/03 (the original's .data): g_tileType[2504] = 0x00572cb0 = byte 0 of g_habitatSlots = 0, type 0 `tees`, flags word

world_to_screen, the same formula). g_tileLevel[2504] = 0x00543018 + 0x9c8 = 0x005439e0 = byte 0 of g_surfaces5439e0[0], which holds
the vtable 0x004ba2d8 that Surface_ctor stores (0x00473ab7; initGlobalArray_00404c20's step 0x00404c85 constructs the 16 elements):
0xd8 = -40, so (-43) * 5 * 4 / 4 = -215 and sy + 215. The neighbour corner (0xc400, 0xd7ff) = cell 2503 = 0x005439df, the last byte
before that object, 0: (-3) * 5 = -15, sy + 15. Base y: 315 - 15 = 300 and 496 - 215 = 281, so with the byte 0 the corner would be
(431, 296), level with the opposite corner (368, 295), as in every regular diamond of 25_group5.log. The 181 px drop is the vtable byte.
The port: tick_boot.inc BootCrt runs only staticInit_820f04, arrayStaticInit_448160, gTerrain and allocTileBuffer, so no Surface vtable
word is ever stored and 0x005439e0 is 0 in the port's state (snapshot cov_b_inject snap2: 0). The port draws the regular diamond.
Not fixed, decision for the lead: reproducing the read needs the vtable word 0x004ba2d8 in the port's GameState, an address of the
user's exe .rdata; port code may hold no original address (port/README.md, test_static). Options: (a) keep (the connector is drawn
only for a cursor tile past the map's y edge; the port's frame shows a regular diamond there); (b) BootCrt performs Surface_ctor's
stores for the static Surface arrays with the vtable value read from the user's exe (the imm32 of Surface_ctor's `mov [eax], imm32`,
a new ExeConstants code descriptor), which also changes worldToScreen results for every out-of-map tile whose reads land in those
objects (a sim function: the segment / boot gates would judge it). Recommendation: (a) now, (b) only with a measured case where the
simulation reads one of those bytes.
